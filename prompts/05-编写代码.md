《编写代码》
请根据已经确认的 PRD、UI 设计、技术方案和实现计划，采用检查点（Checkpoint）模式实现代码。

一次只处理一个检查点。在当前检查点通过验证之前，不要继续实现后面的功能。

## 开始前

1. 阅读 docs/、memory.md 和当前检查点有关的代码，不要重复实现已有功能。
2. 检查项目当前是否能启动、已有测试是否通过，并记录基线结果。
3. 查看当前目录和已有改动。不要删除或覆盖与本检查点无关的内容。
4. 用自己的话说明：
   - 这一步要完成什么；
   - 这一步明确不做什么；
   - 准备修改哪些文件；
   - 用哪些测试样例验证；
   - 通过检查的标准是什么。
5. 如果缺少 API Key、运行环境、测试数据或其他必要条件，先停下来说明缺什么、怎样准备。不要伪造密钥，也不要用假数据冒充真实测试结果。

## 实现规则

1. 只做通过当前检查点所需的最小改动，不提前实现后续功能。
2. 沿用技术方案、目录结构和 memory.md 中已经确认的约定。
3. 保持代码简单、可读。新增依赖前先说明用途；标准功能或现有依赖能解决时，不再引入新的库。
4. 调用外部模型或服务前，先确认：
   - API Key 已通过安全方式配置；
   - .env 已加入 .gitignore；
   - .env.example 只保留变量名，不包含真实密钥；
   - 密钥只在后端或本地安全环境中读取，不写入前端代码；
   - 测试数据已经脱敏；
   - 我知道这次调用可能消耗额度或产生费用。
5. 涉及外部网络、付费调用、上传数据或安装新依赖时，先说明影响，得到我的确认后再执行。
6. 为本次功能补充测试。测试要检查真实结果，不能只检查程序有没有报错。
7. 不要为了让测试变绿而删除测试、降低正确性要求、写死标准答案或吞掉错误。

## 验证顺序

1. 运行与当前检查点直接相关的自动测试；
2. 使用 test_samples/ 中的输入和标准答案核对结果；
3. 启动程序，给出我可以照做的手动检查步骤；
4. 再运行一次已有测试，确认旧功能没有被改坏；
5. 发现失败时先定位原因，只修改一个最可能的地方，然后重新运行同一项测试；
6. 如果仍未通过，保留完整报错和当前现场，不要假装已经完成。

## 记录（CAPTURE）：更新 memory.md

检查点通过后，再判断是否有值得长期保留的新结论。只记录：

- 已确认的设计偏好或项目约束；
- 被事实或测试修正的错误假设；
- 已推翻或拒绝的设计模式，以及原因；
- 下次修改时仍应遵守的规范与约定。

不要把 memory.md 写成开发日志。不要记录普通进度、整段对话、临时猜测、客户隐私或 API Key。没有新的长期结论时，不要为了更新而更新。

## 每个检查点结束时

1. 说明完成了什么，以及哪些内容没有做；
2. 列出修改的文件；
3. 列出实际运行的命令和测试结果；
4. 给出手动检查步骤；
5. 说明 memory.md 是否更新、记录了什么；
6. 列出仍存在的问题或风险；
7. 停下来等待我确认，不要自动进入下一个检查点。

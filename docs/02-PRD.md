# 产品需求说明书（PRD）

> 产品暂定名：**CheckBIM Agent**  
> 版本：MVP v0.1  
> 日期：2026-08-24  
> 依据：[01-业务诉求澄清报告.md](01-业务诉求澄清报告.md) + PRD 澄清对话（Q1–Q5）

---

## 1. 产品名称和一句话介绍

**CheckBIM Agent**：面向 BIM/建筑工程师的对话式检查助手——在模型交付前，用自然语言触发**几何碰撞**与**关键属性完整性**检查，并给出可追溯、可验收的结构化结果与可视化。

---

## 2. 要解决的问题

交付前常见两类基础问题：

1. **几何碰撞**：墙、梁、管道等构件空间冲突，人工翻模难以及时发现。
2. **属性缺失**：Name、FireRating 等关键字段缺失，影响下游合规与协作。

若检查结果不可信（尤其是**漏报碰撞**或**未真正执行检查却编造报告**），用户会带着假安全感交付，代价远高于误报。

本产品用 Agent 编排检查工具，把「意图 → 真实检查 → 可核对结果」做成可运行的第一版。

---

## 3. 目标用户和使用场景

| 项 | 定义 |
|----|------|
| **目标用户** | 产品最终用户：BIM / 建筑工程师（演示叙事亦面向此类用户；评审为观众） |
| **主场景** | **模型交付前自查**：即将交模/出图前，先跑碰撞与属性检查 |
| **次要场景（非 MVP 主流程）** | 收到模型后验收、设计过程中随时抽查 |

---

## 4. 用户完成任务的主要步骤

1. 打开 CheckBIM Agent 界面。
2. **选择模型来源**（双入口之一）：
   - 上传 IFC 文件；或
   - 从内置样例中选择（JSON / 小型 IFC）。
3. 用自然语言说明意图（如「帮我查碰撞」「检查防火属性是否齐全」「两个都查」）。
4. Agent 解析意图 → **实际调用**对应检查工具（不得跳过工具直接生成假结果）。
5. 查看：对话摘要 + 结构化清单（碰撞对 / 缺失属性）+ 基本可视化。
6. （可选）追问某条结果详情；决定是否修正模型后再次检查。
7. （笔试）按同一路径录制 ≤3 分钟演示视频。

---

## 5. MVP 范围（第一版必须实现）

- 对话式 Agent：识别至少下列意图——查碰撞、查属性、两者都查、基于当前结果追问摘要。
- **规则 1：几何碰撞**（墙 / 梁 / 管道等；具体实体集合在技术方案中固化）。
- **规则 2：属性完整性**（至少检查 Name、FireRating 是否缺失；适用构件类型在技术方案中固化）。
- **双入口**：上传 IFC **或** 选择内置样例。
- **双数据**：JSON 支撑自动化测试；IFC 支撑演示。
- 输出：结构化检查结果 + 自然语言解释 + 基本可视化（示意级即可）。
- `test_samples/`：样例输入 + 金标答案；自动测试比对结构化结果。
- 防编造：报告中的命中项必须来自检查工具输出；无工具结果不得宣称「检查通过」。
- 交付物：GitHub（代码 + 提示词）+ ≤3 分钟演示视频。

---

## 6. 本次暂不实现的功能

- 疏散门净宽、房间到出口距离等**第二条几何规范规则**。
- 完整 BIM 规范库 / 全量合规引擎。
- CAD 原生格式深度支持（优先 IFC + JSON）。
- 完整「接收方验收」工作流、多人协作、权限与审计。
- 微服务、消息队列、多租户、复杂 3D BIM 编辑器。
- 多轮深度诊断（如自动给出改模方案并写回 IFC）。

---

## 7. 程序的输入和输出

### 输入

| 类型 | 内容 |
|------|------|
| 用户意图 | 自然语言文本 |
| 模型（二选一） | ① 用户上传的 IFC；② 内置样例 ID（指向 JSON 或小型 IFC） |
| 系统配置 | API Key 等（仅服务端/本地环境，不进入前端） |

### 输出

| 类型 | 内容 |
|------|------|
| 对话回复 | 检查摘要、严重程度说明、建议下一步（自然语言） |
| 碰撞结果 | 冲突对列表（构件 ID/名称、类型、可选位置信息） |
| 属性结果 | 缺失 Name / FireRating 等的构件清单 |
| 可视化 | 列表高亮或简单示意图（3D 高亮为 Should） |
| 追溯信息 | 所用工具名、模型标识、是否真实执行检查（用于防编造与调试） |

---

## 8. 验收标准

| 维度 | 标准 |
|------|------|
| **准确性** | ① JSON 金标：碰撞对数量与关键 ID、缺失属性清单与标准答案一致（允许技术方案规定的规范化排序）；② 演示 IFC：人工抽检 1–2 个**已知碰撞**必须出现在报告中（防漏报）；③ 禁止未调用检查工具却输出「已检查」结论 |
| **处理速度** | JSON 样例检查在本地可交互时间内完成（目标：常见样例 &lt; 30s）；演示 IFC 须选用小文件，保证视频录制不卡死 |
| **隐私** | 上传模型默认本地或自管环境处理；不将客户模型写入公开日志；测试数据脱敏 |
| **安全** | API Key 仅 `.env`；`.env` 进 `.gitignore`；`.env.example` 无真实密钥；密钥不进前端 |
| **预算** | 7 天个人项目；外部模型调用需可关闭或可换本地 fixture，避免演示依赖不可控费用 |

**错误优先级（验收底线）**

1. **最不能接受**：漏报碰撞  
2. **其次**：Agent 编造结果 / 未跑检查却生成报告  
3. 误报碰撞、属性假阴性：应尽量减少，但不以牺牲「漏报防护」为代价盲目放宽阈值

## 9. 测试材料、测试方法和预期正确结果

### 材料（`test_samples/`）

| 样例 | 用途 | 预期 |
|------|------|------|
| `collision_positive.json` | 含已知碰撞对 | 金标列出全部已知碰撞对；漏任一即失败 |
| `collision_negative.json` | 无碰撞 | 结果为空列表（或显式 no_collision） |
| `attrs_missing.json` | 故意缺失 Name/FireRating | 金标列出对应构件与字段 |
| `attrs_ok.json` | 属性齐全 | 缺失清单为空 |
| `demo/*.ifc` | 演示 + 人工抽检 | 文档记录「已知碰撞」1–2 处，演示报告必须命中 |

### 方法

1. **自动**：对 JSON 样例跑检查工具 → 与 `*.expected.json` 比对（结构化字段，不比对对话文案）。  
2. **人工**：对演示 IFC 按已知冲突清单抽检。  
3. **防编造用例**：模拟工具失败/未调用时，Agent 不得输出「检查通过」；应报错或提示重试。

### 预期正确结果

- 金标样例全部自动测试通过。  
- 演示路径可完整走通「选/上传模型 → 对话触发 → 见真实结果」。  
- 漏报与编造相关用例不得失败。

## 10. 设备、数据、网络和技术限制

| 类型 | 限制 |
|------|------|
| **时间** | 7 天交付 |
| **设备** | 普通开发机即可；演示用桌面浏览器 |
| **数据** | 优先小体积 IFC；大模型文件不作为 MVP 默认路径 |
| **网络** | Agent 若调用外部 LLM，需有离线/fixture 退化策略，保证核心检查逻辑可本地验证 |
| **技术** | 栈自选（如 Python + ifcopenshell、Web 前端、Agent 框架）；第一版单体可运行，不过度拆分 |
| **格式** | MVP 支持 IFC + JSON；不承诺 DWG/RVT 原生 |

---

## 11. 容易出错的特殊情况

| 情况 | 风险 | MVP 处理 |
|------|------|----------|
| 空文件 / 非 IFC / 损坏文件 | 崩溃或假结果 | 明确报错，不进入「检查通过」 |
| 超大 IFC | 超时、卡死 | 大小/超时限制 + 提示改用样例或缩小模型 |
| 意图模糊（「帮我看看」） | 调错工具或编造 | 追问或默认「两项都查」，并展示将执行的工具 |
| 仅属性意图却漏跑碰撞（或反之） | 答非所问 | 意图→工具映射可测；结果标明执行了哪些规则 |
| JSON 与 IFC 语义不一致 | 测试绿、演示翻车 | 金标与演示已知冲突文档化；规则参数统一 |
| 工具失败但 LLM 仍「总结」 | **编造** | 无工具成功输出则禁止成功话术 |
| 近似接触被判碰撞 / 阈值过松漏报 | 误报或漏报 | 阈值写入技术方案；优先避免漏报 |
